# この構成は結局なにをやっているのか（初心者向けの全体像）

Ollama + Open WebUI + Playwright を Docker で組み、ローカルLLMに
実ブラウザを操作させるまでの構成を、レストランに例えて説明する。

## 5つの登場人物

| 役割 | 正体 | 何をするか |
| --- | --- | --- |
| 料理人の頭脳 | qwen3:8b（モデル） | 実際に考える本体。80億パラメータのファイル。単体では動かない |
| 厨房 | Ollama（ランタイム） | モデルをメモリに載せて計算させる装置。窓口は 11434 番のAPIのみ |
| 客席とメニュー | Open WebUI（フロント） | ブラウザのチャット画面。注文を受けてOllamaに投げ、結果を整形する |
| コンロの火力 | GPU（RTX 5060 Ti） | 同じモデルでもCPUなら数分、GPUなら数秒 |
| 各部屋 | Docker | 3つのコンテナが独立して動き、サービス名で呼び合う |

Docker内部では localhost は自分自身を指す。だから他コンテナを呼ぶときは
`http://playwright:8000` のようにサービス名を使う。ここが最頻出の罠である。

## LLMに手足を生やす2つの部品

LLMは閉じた箱で、学習データに入っていることしか知らない。
インターネットを見に行く手足を持たない。そこで2つを足す。

- Playwright API … 実ブラウザを操作する別コンテナ。外の世界へ行く足
- Function Calling … モデルに道具の存在を教え、使う判断をさせる仕組み

重要な点として、モデル自身はAPIを叩かない。
モデルがやるのは「この道具をこの引数で使え」という注文票をJSONで書くことだけ。
実際に実行するのは Open WebUI である。ここを取り違えるとデバッグが迷走する。

## 実際の処理の流れ

```
1  ユーザー      ブラウザのチャットに入力
2  Open WebUI   質問 + 道具の定義(get_title) をまとめて Ollama へ送る
3  Ollama       qwen3:8b を GPU に載せて推論
4  qwen3        道具を使う場面だと判断し、注文票を出力
                {"name":"get_title","arguments":{"url":"https://example.com"}}
5  Open WebUI   注文票を読み、自分で Playwright に HTTP リクエスト
6  Playwright   実ブラウザでページを開き、タイトルを抽出して返す
7  Open WebUI   結果を qwen3 に戻して再度推論させる
8  qwen3        受け取った結果を自然な文章にする
9  ユーザー      画面にタイトルが表示される
```

9ステップすべてがローカルPC内で完結し、外部にデータが出ない。
これがこの構成の最大の価値である。

## 今日詰まっていた箇所

ステップ2から4の間で、Open WebUI が道具の定義をモデルに渡していなかった。

- Default モード … 道具の説明を文章で埋め込み、返答を正規表現でパースする。8Bクラスには荷が重く失敗する
- Native モード … 正式な tools 配列として渡す。モデルが学習済みの形式で応答できる

Native に切り替え、組み込みツールを全部オフにして get_title 1個だけにしたら通った。
詳細な切り分け手順は FUNCTION-CALLING.md を参照。

## ここから何ができるか

get_title が通ったということは、型が完成したということである。
Playwright API に関数を1つ足し、docstring を書けば、それがそのまま
LLM の新しい能力になる。

- スクリーンショットを撮る
- 本文テキストを抽出する
- ページ内のリンク一覧を取る
- フォームに入力して送信する

作ったのはタイトル取得ツールではなく、ローカルLLMに手足を生やす仕組みそのものである。
